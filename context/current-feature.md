- Auth Phase 4, email verification on register — registration now issues a verification token and emails the link through Resend; `GET /verify-email?token=…` consumes it, stamps `User.emailVerified` and deletes the row, and credentials sign-in is refused until that happens. **No migration**, as targeted: `User.emailVerified` and `VerificationToken` have been in the schema since the Prisma feature, and the latter was otherwise unused because Auth.js only touches it for a magic-link provider. `resend` (6.22.1) is the one new dependency. The link is a bearer credential — anyone holding it can verify that account — so only a **SHA-256 digest** is stored and the email carries the only copy of the plaintext; a plain digest suffices where a password needs bcrypt, since the input is 256 random bits with no dictionary to run against it. Confirmed live: the column holds 64 hex characters, the emailed token 43. Tokens last 24h and work exactly once, deleted on use **and on every failure branch**. **The security detail that drove the design:** the `emailVerified` check sits *after* the bcrypt comparison, never before it — reversed, it would answer "is this address registered?" for anyone who asked. Verified rather than assumed: an unverified account with the *wrong* password returns `code=credentials`, byte-identical to an unknown email, while only a correct password returns `code=email_not_verified`. That specific message was chosen over the generic one because `/register` already returns 409 for a taken address, so nothing is disclosed that was not already, and the alternative strands a legitimate user on "Invalid email or password". The gate is **credentials-only**: GitHub's profile mapping never sets `emailVerified`, so gating it would lock every OAuth account out. Auth.js turned out to rethrow the thrown error object itself to a server action rather than only encoding it in a redirect — `if (isAuthError && isRaw && !isRedirect) throw error` in `@auth/core/index.js` — so `EmailNotVerifiedError extends CredentialsSignin` carries its `code` straight into `src/actions/auth.ts`, read out of `node_modules` rather than assumed. `new Resend(undefined)` **throws at construction**, proven by running it, so the client is built lazily; a top-level instance would break any `next build` without the key. The SDK also reports failures in `error` instead of throwing, so both halves are handled — and a failed send never fails the registration, since the account exists either way and the 500 would read as "try again" when only the duplicate-email path awaits. The resend action replies identically for an unknown address, an already-verified account and a real send. **A real defect found in testing, not at load:** `VerificationToken` has no foreign key to `User` (it is keyed on the email string), so deleting an account orphaned its token and an unclicked link never expired away — the table grew without bound.
